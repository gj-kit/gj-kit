### 1.2 iOS HealthKit — reading

11. Use the async query descriptors: `HKSampleQueryDescriptor`, `HKAnchoredObjectQueryDescriptor` (returns `addedSamples`, `deletedObjects`, `newAnchor`; `anchor == nil` reads everything), `HKWorkoutRouteQueryDescriptor(route).results(for:)` (finite `AsyncSequence<CLLocation>`), `HKStatisticsQueryDescriptor`. `[official-doc]` healthkit-read f1–7
12. `HKWorkout.duration` is **active** time (pause/resume events subtracted); `endDate − startDate` is elapsed. `totalEnergyBurned` deprecated iOS 18 (warning), `totalDistance` `API_TO_BE_DEPRECATED` (no warning, formally iOS 27). Read totals in this order: `statistics(for:)` (associated samples) → deprecated totals → time-window statistics tagged `derived`. ~~`statistics(for:)` is `nil` when the writer associated no samples~~ — **CORRECTED by Phase 0 T2 (f71–f74):** on iOS 26.5 HealthKit *synthesises* an `HKStatistics` from the deprecated totals, so `statistics(for:)` returns `totalDistance`/`totalEnergyBurned` for totals-only workouts and is `nil` only when there are neither samples nor totals. Tier 2 is therefore currently unreachable, and tier 1 alone cannot tell `associated` from `total` — add a `predicateForObjects(from: workout)` sample query to decide provenance. Also measured: `duration` honours the writer's explicit argument (1500 s) while `end − start` is 1800 s. `[official-doc][source-code][sim-test]` healthkit-read f8–10, followup-2 f26–30, **phase0 f71–f76**
13. Routes: one workout may have 0..n `HKWorkoutRoute` samples, attached **after** the workout and possibly **replaced later** via sync identifier (Apple Watch smoothing) → find routes with an anchored query on `HKSeriesType.workoutRoute()` + `HKQuery.predicateForObjects(from: workout)`, then stream locations. Stored `CLLocation` subset: `timestamp, coordinate, altitude, speed, course, horizontalAccuracy, verticalAccuracy, speedAccuracy, courseAccuracy` (negative = invalid sentinel). **Phase 0 T7 (f83): all nine fields round-trip bit-identical, explicit `0` is preserved (not turned into −1), and negative sentinels are preserved on the way IN as well as OUT** — a −1 reaching JS can come from HealthKit or from the writing app. `[official-doc][sim-test]` healthkit-read f16–19, **phase0 f83**
14. Read authorization is **opaque by design**: `authorizationStatus(for:)` reflects sharing only; denied reads look like empty data; `statusForAuthorizationRequest` only says whether a sheet will appear. iOS 27 beta adds a per-type limited-access window (`earliestAuthorizedSampleDate(for:)`) — "treat data before that date as unknown, not absent". `[official-doc]` healthkit-read f30–33
15. Time window: HK default predicate is **overlap**; pass `.strictStartDate` to get "start in `[from,to)`" — identical to Health Connect's `readRecords` (start-time column only). HC `aggregate` uses overlap — never mix aggregate buckets with record windows. **Phase 0 T11 confirmed both halves of the read rule with boundary evidence on both platforms (f87, f107) and added f108: HC's `LocalDateTime` overloads query a different column and put the same record in a different day bucket — never expose them.** The `aggregate` half is *not* confirmed: `aggregate()` returned `null` for every metric on the test device (f109). `[source-code][sim-test][device-test]` followup-3 f31–35, **phase0 f87, f107–f109**
16. Writer identity: `sourceRevision.source.bundleIdentifier` vs `Bundle.main.bundleIdentifier` (or exclude at query time with a NOT predicate on `HKSource.default()`). Apple Watch first-party workouts appear as `com.apple.health.<UUID>` `[secondary]`. `[official-doc]` healthkit-read f28
17. Anchors: `HKQueryAnchor` is `NSSecureCoding` → `NSKeyedArchiver.archivedData(withRootObject:requiringSecureCoding: true)` → base64; `HKDeletedObject` carries only `uuid` + sync id/version and **can be purged by the system** → the sync API needs a reset/full-resync path. Anchored results are not date-ordered `[unverified]`. `[official-doc]` healthkit-read f25–26
18. Heart rate: `workout.statistics(for: .heartRate)` gives avg/min/max for Apple Watch workouts; third-party workouts may have no associated samples → time-window `HKStatisticsQueryDescriptor` fallback (may pick up other sources; tag provenance). Older first-party workouts are **condensed** into series samples — use statistics, never raw sample counts. `[official-doc]` healthkit-read f21–23
19. Entitlements/plist: `com.apple.developer.healthkit` (Bool), `NSHealthShareUsageDescription` (read), `NSHealthUpdateUsageDescription` (write) — missing strings **crash** at `requestAuthorization`. Do not write `com.apple.developer.healthkit.access` (clinical records only). Expo prebuild does **not** add `healthkit` to `UIRequiredDeviceCapabilities` (only the Xcode UI does) — keep it that way. `[official-doc][source-code]` healthkit-read f35, followup-4 f11–12
20. HealthKit works on the iOS 26.5 **simulator** (Health.app + Fitness.app present); background delivery does not. No `simctl` command seeds or pre-grants Health; the simulator Health app can add a workout but **not a route** → route fixtures come only from our own write path. `[sim-test]` healthkit-read f42–43, testing-e2e f1–5

### 1.3 iOS HealthKit — writing (simulator-verified where marked)

21. Only non-deprecated path: `HKWorkoutBuilder` (`beginCollection` → `addSamples`/`addWorkoutEvents`/`addMetadata` → `endCollection` → `finishWorkout() -> HKWorkout?`). Every `HKWorkout(activityType:…)` initialiser and `HKHealthStore.add(_:to:)` are deprecated since iOS 17. `[official-doc][source-code]` healthkit-write f1–3, f38
22. Route builder: `insertRouteData([CLLocation])` (any order; sorted on finish; an insert error is fatal for that builder) then `finishRoute(with: savedWorkout, metadata:)`; the workout must already be saved; a route can never be re-parented; a builder deallocated before finish **loses all points** — keep builders strongly referenced across the JS call boundary. **Phase 0 confirmed the ordering (f83) and added four behaviours the pack did not have: points sharing a timestamp are silently de-duplicated, last-inserted wins, even across separate `insertRouteData` calls (f82); `finishRoute` with zero points throws `HKError 3 "No data was added to the workout route."` (f84); an insert error *silently poisons* a series builder so later inserts return `ok` and the workout finishes route-less with no error (f64); an unfinished builder leaves a non-queryable partial series row that `deleteObjects` still counts (f69).** `[official-doc][source-code][sim-test]` healthkit-write f13–16, **phase0 f64, f69, f82–f84**
23. **RESOLVED by Phase 0 T1 — use the DIRECT builder (path B).** ~~Unresolved contradiction (device test T1)~~. The SDK header wins over Apple's article on iOS 26.5: `finishWorkout()` auto-finishes and auto-associates a `seriesBuilder(for:)` route (f61), and a subsequent explicit `finishRoute(with:)` throws `HKError 3 "This route builder is attached to a workout builder…"` on a write that already succeeded (f62) — Apple's article step 5 is wrong as written. But the **direct** `HKWorkoutRouteBuilder(healthStore:device: nil)` is now the **PRIMARY** path, not a fallback, because only it can attach a route to a workout re-fetched by UUID after saving (f66 — required for the `pendingUnlock` retry), its every failure is an explicit typed error, and it never risks the workout (f63) — whereas a poisoned series builder silently yields a route-less workout (f64) and `discard()` on one destroys the workout save entirely (f65). Route metadata is **not** a discriminator: `addMetadata` works on the series-builder path too (f67). The locked-device field report could not be reproduced (f70, see f24). `[source-code][official-doc][sim-test]` followup-1 f30–35, followup-2 f1–12, **phase0 f61–f70**
24. Locked device: `finishWorkout()` returns `nil` workout **and** `nil` error = success-but-unavailable ("query for it once the device unlocks" — Apple Frameworks Engineer); `finishRoute` can fail with `errorDatabaseInaccessible`. The JS contract needs a `pendingUnlock` outcome and an idempotent retry. **Phase 0 could NOT reproduce this (f70): the simulator has no `health` privacy service and no way to force protected-data-unavailable, and no physical iPhone was available. It stays source-only and must be designed for defensively.** Retry shape proven in f66: re-query by sync id, then a **fresh** direct route builder on the re-fetched workout. `[official-doc][source-code][unverified]` healthkit-write f5, f48, followup-2 f5–7, **phase0 f70**
25. Apple's client-side hygiene (HealthKit documents **no** server-side filtering): drop `horizontalAccuracy > 50 m` or negative, keep ≤ 3 s between points. **Phase 0 T7 CONFIRMED the "no server-side filtering" half far more strongly than stated (f81, f85): `hAcc=80`, `hAcc=−1`, points 60 s before start and 60 s after end, negative altitude/speed/course sentinels, and even `lat=91` / `lon=181` are all stored and read back byte-identical. Our layer owns 100 % of the hygiene.** ~~DTS says routes whose timestamps fall outside the workout window "typically" do not render in Fitness~~ — **REFUTED for Health.app on iOS 26.5 (f86): the route renders including the out-of-window points, with the start/end pins placed on them.** Fitness.app itself was unreachable (personal-details onboarding), so the claim may still hold for Fitness only. `[official-doc][secondary][sim-test]` healthkit-write f18–21, followup-3 f1–7, **phase0 f81, f85, f86**
26. **Upsert (`[sim-test]`, iOS 26.5):** saving with the same `HKMetadataKeySyncIdentifier` and `HKMetadataKeySyncVersion` **≥** existing replaces the workout with a **new UUID** (docs say "greater"; equal also replaces); a **lower** version throws `com.apple.healthd.SQLite Code=1`. The replacement does **not** carry the old workout's associated samples/route — they are **orphaned** (still counted in Health) and `store.delete(workout)` does **not** cascade. `store.addSamples(oldSamples, to: newWorkout)` re-attaches them without duplication. Routes: re-save with its own sync id (`${id}/route`) replaces (equal version too); a lower route version silently returns the existing route's UUID. **Phase 0 added a hazard (f68): the replacement route INHERITS the replaced route's workout association in addition to its own — after replacing a route from workout w1 under workout w2, `predicateForObjects(from: w1)` returns w2's route. Route sync identifiers MUST be derived per workout and never reused across workouts.** `HKMetadataKeyExternalUUID` is **not** unique. `[sim-test]` followup-4 f7–8, raw: `expo-workouts/hkprobe/hkprobe-run*.txt`
27. Own writes echo in own anchored queries; a re-save surfaces as `deleted=[oldUUID (metadata: sync id + version)]` + `added=[newUUID]` → "replaced" vs "removed" is distinguishable. `[sim-test]` followup-4 f36–37
28. `discardWorkout()` does not delete samples already pushed via `addSamples` (orphans on failure); `HKQuantitySample` init with a wrong unit or `start > end` raises an ObjC exception (crash, not a throw) — validate in Swift first; `earliestPermittedSampleDate()` and ≥ 24 h samples fail with `errorInvalidArgument`. `[official-doc][source-code]` healthkit-write f6, f35–37
29. Share permissions needed for writing: `workoutType()`, `HKSeriesType.workoutRoute()`, every quantity type attached (`distanceWalkingRunning` / `distanceCycling`, `activeEnergyBurned`, `heartRate`, `stepCount` when written). Missing route/workout share permission shows up as an opaque XPC error. `[official-doc][secondary]` healthkit-write f24–26
30. `HKWorkoutSession` / `HKLiveWorkoutBuilder` on iPhone exist since iOS 26 but are **out of scope** (D3); a beta bug hangs route inserts with the live builder on the simulator — one more reason to use the plain builder. iOS 18 effort score must be *related*, not added; iOS 27 zones are beta. `[official-doc][source-code][secondary]` healthkit-write f41–47

### 1.4 Android Health Connect — reading

31. Availability: `HealthConnectClient.getSdkStatus(context)` → `SDK_UNAVAILABLE` (API < 28, work profile, bad signature), `SDK_UNAVAILABLE_PROVIDER_UPDATE_REQUIRED` (API 28–33 without the Play APK ≥ versionCode 68623), `SDK_AVAILABLE`. Play deep link for the update case: `market://details?id=com.google.android.apps.healthdata&url=healthconnect%3A%2F%2Fonboarding`. On API 34+ the provider is the APEX `com.google.android.healthfitness` (UI `com.google.android.healthconnect.controller`); `com.google.android.apps.healthdata` is **not** an installed package there — never check availability via `PackageManager`. **Phase 0 f88 strengthens this: `getPackageInfo` throws `NameNotFoundException` for BOTH `com.google.android.apps.healthdata` AND `com.google.android.healthfitness`; only `com.google.android.healthconnect.controller` resolves. `getSdkStatus(context) == 3` is the only working signal.** Phase 0 f119 also settles the settings intents: `android.health.connect.action.HEALTH_HOME_SETTINGS` resolves and `androidx.health.ACTION_HEALTH_CONNECT_SETTINGS` **does not** on API 36; the `market://` deep link and its `https://play.google.com` equivalent both resolve. `[source-code][sim-test][device-test]` health-connect-read f6–8, testing-e2e f17, followup-3 f37, **phase0 f88, f119**
32. Permission strings: `android.permission.health.READ_EXERCISE`, `WRITE_EXERCISE`, `WRITE_EXERCISE_ROUTE` (singular), `READ_EXERCISE_ROUTES` (plural; API 35 / API 34 via SDK ext 12; present only from HealthFitness module `android14-qpr2`), `READ_HEALTH_DATA_HISTORY` (qpr3), `READ_HEALTH_DATA_IN_BACKGROUND` (qpr2), plus per-type `READ_DISTANCE`, `READ_ACTIVE_CALORIES_BURNED`, `READ_ELEVATION_GAINED`, `READ_HEART_RATE`, `READ_STEPS`. All `dangerous` in group `HEALTH`. `[official-doc][source-code]` health-connect-read f10–15, followup-1 f1–3, followup-3 f13–14
33. **`READ_EXERCISE_ROUTES` cannot be requested**: the platform's permission UI silently filters it from the request set ("attempts to request the permission by applications will be ignored"); it is granted only in Health Connect Settings or via the per-route dialog's ~~**"Allow all"**~~ button. It **must be declared in the manifest** or `RouteRequestActivity` finishes with `RESULT_CANCELED` (→ `null`) without showing anything. `getGrantedPermissions()` lists it once granted. **Phase 0 T5 measured the real Android 16 labels (f111): `Allow this route` (one-shot, does NOT grant the permission) / `Allow all routes` (grants it, flag becomes `USER_SET`) / `Don't allow`. A THIRD grant path exists that the pack does not describe (f117): Settings → app → Manage app → Additional access → Access exercise routes → `Always allow` / `Ask every time` / `Don't allow`. And a trap (f110): the contract's returned set means "granted NOW", not "the user just granted" — it will contain `READ_EXERCISE_ROUTES` if the scope was already held, although no row is ever rendered for it.** Beware a name collision: the *permission-request* dialog also has an "Allow all" control, but that is a master **switch** over the requested data types (f121). `[source-code][device-test]` followup-1 f4–7, followup-2 f48–53, **phase0 f110, f111, f117, f121**
34. Route access rule (service source): routes are attached for **all** sessions only when the caller is in the foreground (AppOps uid state, i.e. process importance — a foreground service counts, a WorkManager job does not) **and** holds `READ_EXERCISE_ROUTES`; otherwise only the caller's **own** sessions' routes, and only while it still holds `WRITE_EXERCISE_ROUTE` or `READ_EXERCISE_ROUTES` (after revocation even own routes become `ConsentRequired`). `READ_HEALTH_DATA_IN_BACKGROUND` does **not** unlock foreign routes (Jetpack KDoc is wrong). Jetpack maps `route == null && hasRoute → ExerciseRouteResult.ConsentRequired`, else `NoData`. **Phase 0 T5 CONFIRMED all of this on device with a 13-row matrix (f113, f114), including that `READ_HEALTH_DATA_IN_BACKGROUND` unlocks the session records but NOT foreign routes, and that own routes become `ConsentRequired` once both route permissions are revoked. It also found an undocumented precondition (f115): Health Connect's FIRST-RUN ONBOARDING must have been completed on the device, or every foreign route reads `ConsentRequired` even with the permission granted and the app in the foreground.** (An intermediate lane briefly reported this fact as refuted; that observation was the not-onboarded state — see §6.) **f116 adds a cost the pack did not price: once route permission is held, every `readRecords` page eagerly materialises every route in it — 139 423 points → 435–792 ms vs 23–55 ms without access, with no request option to suppress it.** `[source-code][official-doc][device-test]` followup-1 f9–11, followup-2 f54–56, **phase0 f113–f116**
35. Per-session consent: `ExerciseRouteRequestContract : ActivityResultContract<String /*sessionId*/, ExerciseRoute?>`; `null` is ambiguous (denied / no route / 30-day wall / permission undeclared / `USER_FIXED` after repeated denials); the route crosses Binder as a plain Intent extra on this path. **Phase 0 T5 confirmed four of the five causes on device and added two (f112): a MALFORMED session id also returns `null` (in direct contrast to `deleteRecords`, which throws for the same string — f96), while an EMPTY session id throws `IllegalArgumentException("Session identifier can't be empty")` client-side before any IPC. Timing is the only weak signal: a real dialog costs seconds, every silent-cancel path returns in 116–134 ms.** **Phase 0 T4 also found the Intent path's own ceiling is ~512 KiB, not 1 MB (f103), and that on overflow the ActivityResult callback NEVER FIRES (f104) — the promise hangs unless the launcher carries a timeout.** `[source-code][device-test]` followup-1 f7–8, followup-2 f46, f52, f57, **phase0 f103, f104, f112**
36. `ExerciseSessionRecord` fields: `exerciseType` (`RUNNING=56`, `RUNNING_TREADMILL=57`, `WALKING=79`, `HIKING=37`, `BIKING=8`, `BIKING_STATIONARY=9`, `OTHER_WORKOUT=0`; unknown future ints collapse to 0), `startTime/endTime`, nullable `startZoneOffset/endZoneOffset`, `title`, `notes`, `segments` (pause = `EXERCISE_SEGMENT_TYPE_PAUSE` 39, rest 44), `laps`, `exerciseRouteResult`, `metadata` (`id`, `dataOrigin.packageName`, `clientRecordId`, `clientRecordVersion`, `lastModifiedTime`, `device`, `recordingMethod`). `ExerciseRoute.Location` = `time, latitude, longitude, altitude?, horizontalAccuracy?, verticalAccuracy?` — **no speed/course**. Health Connect has **no stored active duration** → derive `activeDurationS = (end − start) − Σ PAUSE segments`. `[source-code]` health-connect-read f25–30, domain-model f9, f15, f19
37. Distance / calories / elevation / HR / steps are **separate records linked only by time range** (+ `dataOriginFilter`); read them with one `aggregate(AggregateRequest(metrics, TimeRangeFilter.between(session.start, session.end), dataOriginFilter = setOf(session.metadata.dataOrigin)))`; each metric needs its own READ permission (catch per metric group). **⚠️ CORRECTED by Phase 0 T11 (f109): `aggregate()` returned `null` with an empty `dataOrigins` set for EVERY metric on the test device — before and after Health Connect onboarding — on records the same app had just written and could read via `readRecords`, with no exception thrown. The module MUST treat a null aggregate as UNKNOWN (never zero) and MUST ship a `readRecords` + client-side-sum fallback. Root cause unresolved.** Use `ActiveCaloriesBurnedRecord.ACTIVE_CALORIES_TOTAL`, **not** `TotalCaloriesBurnedRecord.ENERGY_TOTAL` — the latter is synthesised from active + BMR for empty intervals and is almost never null. `[official-doc][source-code]` health-connect-read f34, followup-2 f31–35
38. Paging: `ReadRecordsRequest(pageSize ≤ 1000 default, pageToken)`; by-id `readRecord` of a foreign record older than the 30-day wall **throws**, bulk reads silently truncate. Changes API: `getChangesToken(ChangesTokenRequest(recordTypes))` → `getChanges(token)` (`UpsertionChange(record)` / `DeletionChange(recordId)` — id only, no type), `hasMore`, `changesTokenExpired` (idle > 30 days; also after an Android 13→14 migration). Change logs **include own writes** → filter by `dataOrigin.packageName`. Take the token **before** the backfill read. `[official-doc][source-code]` health-connect-read f33, f36–37, followup-4 f29–31
39. Rate limits are not published; AOSP 15/16 constants: reads 2000 / 15 min FG, 16 000 / 24 h FG, 1000 / 15 min BG, 8000 / 24 h BG; writes 1000 / 15 min, 8000 / 24 h; the emulator shows server-pushed `RateLimiter__*` flags (1000 / 5000) with no AOSP reader. Plan for **1000 / 15 min and 5000 / 24 h**. Exceeding → `HealthConnectException(ERROR_RATE_LIMIT_EXCEEDED = 7)`, surfaced by Jetpack (API 34+) as `IllegalStateException` with that cause (8 = data-sync-in-progress, 9 = unsupported); `IOException`/`RemoteException`/`SecurityException`/`IllegalArgumentException` map 1:1; pre-34 IPC path throws `UnsupportedOperationException` for provider-missing cases and has no rate-limit code. `[source-code]` followup-3 f22–26, followup-4 f24–27
40. Play policy: the **Health apps declaration** in Play Console (Policy › App content) is mandatory for closed testing, open testing and production (internal testing unmentioned), covers read **and** write data types, is reviewed with the release, and every data-type change re-triggers it; unapproved published apps show users a "can't access Health Connect" dialog. No published review SLA (community: ~7 days). `[official-doc][unverified]` followup-1 f38–45

### 1.5 Android Health Connect — writing (source-verified; device test T6 pending)

41. Route is a **field** of `ExerciseSessionRecord(exerciseRoute = ExerciseRoute(locations))`; locations must have **strictly increasing** timestamps (duplicates throw) inside `start <= t < end` (the Jetpack check is end-exclusive, the Android 14+ platform check inclusive — use `< end`); lat ∈ [−90, 90], lon ∈ [−180, 180], accuracies ≥ 0. No documented point cap, but a single record is capped at **1 000 000 parcel bytes** (`ERROR_RATE_LIMIT_EXCEEDED` = errorCode 7, `"Record size exceeded the single record size limit"`) ~~≈ 16.6k points with all optional fields / 27k bare~~; a request is capped at 5 MB. **The cap and its surfacing are CONFIRMED exactly by Phase 0 T4; the point estimates are WRONG (f99, f100). Measured on API 36: `bytes = 160 + 48·points + 2·(title+notes+clientRecordId chars) + 24·(segments+laps)`. A route point costs 48 bytes WHETHER OR NOT altitude/accuracies are set — a 21 000-point route serialised to the byte-identical 1 008 160 B in both shapes. There is ONE threshold: 20 828 OK, 20 829 FAIL at 1 000 004 B.** Phase 0 also confirmed on device that HC throws on duplicate route timestamps while HealthKit silently de-duplicates (f82) — our layer must normalise. `[source-code][device-test]` health-connect-write f10–13, followup-2 f43–46, **phase0 f99–f102**
42. Metadata: constructor is internal since 1.1.0-alpha12 → `Metadata.activelyRecorded(Device(type = Device.TYPE_PHONE), clientRecordId, clientRecordVersion)`; zone offsets from `ZoneId.systemDefault().rules.getOffset(instant)` (or the caller's offset). The official workouts-guide snippet no longer compiles. `[source-code][official-doc]` health-connect-write f15–17, f25
43. **Upsert (source, android15/16/main):** same `(package, clientRecordId, recordType)` ⇒ deterministic name-based UUID ⇒ conflict ⇒ update when `newVersion >= existing`, **silent no-op** when lower; never duplicated ("written as new data" in the sync-data guide is wrong). Upserting a session **without** a route while holding `WRITE_EXERCISE_ROUTE` **deletes the stored route** → `saveWorkout` must always be full-state. Route rows cascade on session delete; metric records do not. `deleteRecords` with an unknown id: KDoc says IPC failure, the Android 14+ code path does not throw. **Phase 0 T6 CONFIRMED every clause on device (f92–f98) and added three: (a) the deterministic UUID is NOT freed by deletion — re-inserting the same `clientRecordId` yields the same UUID (f92); (b) the stale-version no-op is silent to the CHANGES API TOO — `insertRecords` returns the record's UUID and the next `getChanges` drain reports one `UpsertionChange` carrying the UNCHANGED record, so read-back is the only detection (f94); (c) a MALFORMED recordId string THROWS `IllegalArgumentException` caused by `HealthConnectException(errorCode 3, ERROR_INVALID_ARGUMENT)` while unknown ids stay silent (f96).** Metric records confirmed not to cascade; the route does (f98). `[source-code][device-test]` followup-1 f14–24, followup-4 f18–22, **phase0 f92–f98**
44. Value validation: `StepsRecord(count = 0)` throws; HR bpm must be 1..300; negative distance/energy throw; interval records need `start < end`. Validate before the native call or the whole transaction fails. `[source-code]` health-connect-write f23
45. Write only `ActiveCaloriesBurnedRecord` for energy (semantic match for HK `activeEnergyBurned`; Google's sample writes Total but that includes BMR); each written type is another Play-declared data type. `[source-code][official-doc]` followup-2 f31–36

### 1.8 Domain model & sync numbers

57. Pause semantics: HK pause(1)/resume(2) events (+ motionPaused/Resumed = Watch auto-pause; whether subtracted from `duration` is undocumented) vs HC `PAUSE` segments; laps: HK lap events (pre-iOS-11 laps are zero-duration end markers) vs HC `ExerciseLap(start, end, length?)`. `[official-doc][source-code]` domain-model f11–19
58. Energy: HK `activeEnergyBurned` excludes resting; HC `TotalCaloriesBurned` includes BMR → unified `activeEnergyKcal` maps to HK active / HC `ActiveCaloriesBurned`; kcal everywhere (platforms, TCX/GPX, Strava all use kcal). Elevation: HK metadata `HKElevationAscended/Descended` vs HC `ElevationGainedRecord` (no loss record). Time zones: HK optional IANA `HKTimeZone` vs HC fixed `ZoneOffset` → `utcOffsetMin` in the common model, IANA id under `platformData.ios`. `[official-doc]` domain-model f20–28, f43–44
59. Route payload (1 h at 1 Hz, 3 600 points, computed): JSON objects ≈ 390 KB (65 KB gzip); positional arrays ≈ 150 KB (35 KB gzip); varint deltas ≈ 18 KB; Google polyline (2-D only) ≈ 7 KB. Keep full resolution on the server; derive polylines for thumbnails; Douglas-Peucker kept 287/181/102/65/41 of 3 600 points at ε = 1/2/5/10/20 m on a synthetic track. GPX export is a cheap pure-TS concern but **belongs to a separate focused package** (medalmedal2 AGENTS.md). `[computed][official-doc]` domain-model f51–56
60. Cross-source duplicates are normal (Strava imports Apple-Workout-app workouts only and writes back; Garmin → HC one-way without routes): dedupe key `(platform, nativeId)` plus a secondary `(source.id, kind, start±1 s, end±1 s)` index that flags rather than merges. `[vendor docs]` domain-model f47–50

## 4. What a clean minimal API must avoid (from the library audit)

- Boolean permission results and pretending iOS read status is knowable → per-scope states incl. `unknown`.
- Eager giant route arrays, per-call native leaks, `try!` → streamed chunks, strong builder references, typed errors.
- `initialize()` ceremony, raw platform identifiers / permission strings / `HKUnit` / `Length` objects on the JS surface.
- Unit asymmetry read-vs-write (AE miles, matinzd `{value, unit}` on write vs `inMeters` on read) → SI only, unit in the field name.
- Sync APIs whose first call returns nothing without explaining the backfill → cursor contract with an explicit initial backfill and `reset`.
- Plugins that leave `<uses-permission>` to the app (matinzd) → the plugin/manifest owns every declared permission; app provides only strings + privacy-policy URL.
- Background observers in v1 (largest issue cluster, needs AppDelegate mutation, untestable on the simulator).

### Corrections made by Phase 0 measurement (2026-08-22)

These overwrite the corresponding claims in §1 above (already edited in place) **and** in the underlying reports. Full evidence in [`expo-workouts/phase0/RESULTS.md`](./expo-workouts/phase0/RESULTS.md).

- **§1.2 f12 / §2 "HK totals fallback order" / `healthkit-read.md` f8–10 / followup-2 f26–30 — REFUTED.** `statistics(for:)` is **not** nil for a workout written with the deprecated `HKWorkout(...totalEnergyBurned:totalDistance:)` initialiser: iOS 26.5 synthesises `HKStatistics` from the totals (measured 4321 m / 123 kcal, reproduced at 2222 m / 77 kcal). - **§1.3 f22 / `healthkit-write.md` f13–16 — CONFIRMED plus four new behaviours:** timestamp de-duplication on write (last wins, across calls), `finishRoute` on an empty builder throws, an insert error silently poisons a series builder, and unfinished builders leave non-queryable partial rows. (phase0 f64, f69, f82, f84)

But the DTS "out-of-window routes typically do not render in Fitness" claim is not reproduced: Health.app renders them, start/end pins included. Fitness.app was unreachable, so the claim may survive for Fitness only. (phase0 f81, f85, f86)
- **§1.3 f26 / followup-4 f8 — CONFIRMED plus a hazard.** A replacement route **inherits the replaced route's workout association**, cross-linking both workouts. Route sync identifiers must be per-workout. (phase0 f68)

That was an artefact of **Health Connect's first-run onboarding never having been completed** on the AVD; after tapping "Get started" the identical scenario returns `Data`. Decisive control: an app whose permissions were installed with `pm grant` only (no `USER_SET` flag, never through any HC UI) reads a foreign route inline as `Data`. The AOSP rule holds exactly. **New documented precondition: the device must have been onboarded.** (phase0 f115)
- **§1.4 f33 / followup-2 f51 — LABELS CORRECTED.** The per-route dialog's buttons on Android 16 are `Allow this route` / `Allow all routes` / `Don't allow`, not "Allow / Allow all / Don't allow". A third grant path exists (Settings → Additional access → Access exercise routes). The permission-request dialog's "Allow all" is a **switch** over data types, not a route control. (phase0 f111, f117, f121)
- **§1.4 f33 / followup-2 f48–49 — SHARPENED.** The request contract's returned set means "which requested permissions are granted **now**", so it will contain `READ_EXERCISE_ROUTES` if it was already held — never read its presence as "the user just granted it". (phase0 f110)
- **§1.4 f35 / followup-1 f7–8 — CONFIRMED plus two.** A *malformed* session id also returns `null` (contrast `deleteRecords`, which throws for the same string); an *empty* session id throws client-side before any IPC. - **§1.4 f37 / `health-connect-read.md` f34 / followup-2 f31–35 — UNRELIABLE.** `aggregate()` returned null with empty `dataOrigins` for every metric on the test device, before and after onboarding, on records readable via `readRecords`, with no exception. - **§1.5 f41 / `health-connect-write.md` f10–13 / followup-2 f43–46 — POINT ESTIMATES WRONG.** The 1 000 000-byte cap and its `errorCode 7` surfacing are exact; "≈16.6k with optional fields / 27k bare" is not. Optional route fields are **free**; there is one threshold at 20 828 points. (phase0 f99, f100)
- **§1.5 f43 / followup-1 f14–24 — CONFIRMED plus three**, most importantly that the stale-version no-op emits an `UpsertionChange` too. (phase0 f92–f98)
- **§1.7 f51–f53 / `testing-e2e.md` — AUTOMATION PREREQUISITES EXTENDED.** iOS: boot windowed or the sheet never appears; `-parallel-testing-enabled NO` or you read a stale container.
