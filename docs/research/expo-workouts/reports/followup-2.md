## 1. Facts

### Item 1 — HealthKit route write protocol

1. `HKWorkoutRouteBuilder.h` (iOS 26.5 SDK) class comment: "If the discard method is called, collected data will be deleted. Calling finishRouteWithWorkout:metadata: will stop and complete the route. If the builder is deleted, or the client goes away before calling the finish method, data will be lost." [source-code] `/Applications/Xcode.app/.../iPhoneOS26.5.sdk/System/Library/Frameworks/HealthKit.framework/Headers/HKWorkoutRouteBuilder.h`
2. Same header, `initWithHealthStore:device:`: "The designated initializer to create an HKWorkoutRouteBuilder. If you are using an HKWorkoutBuilder , you should not create an HKWorkoutRouteBuilder, instead use -[HKWorkoutBuilder seriesBuilderForType:]". No `API_DEPRECATED` on the initializer; class is `API_AVAILABLE(ios(11.0), watchos(4.0), macCatalyst(13.0), macos(13.0))`, `NS_SWIFT_SENDABLE`. → "discouraged, works, not deprecated" CONFIRMED. [source-code] same file
3. Same header, `finishRouteWithWorkout:metadata:completion:` abstract: "If you are using this route builder with a workout builder, you should never call this method. The route will be finished when you finish the workout builder." Discussion: "If no series data was added, then workoutRoute will be nil and an error returned. The receiver will be considered invalid afterwards"; completion: "an error will indicate why the series could not be returned including database inaccessibility during device lock." [source-code] same file
4. `HKWorkoutBuilder.h`, `seriesBuilderForType:`: "Retrieves, and creates if it does not already exist, the series builder for the specified type. The series constructed with the returned builder will be associated with the workout when it is finished." Return type `nullable __kindof HKSeriesBuilder *`. [source-code] `.../Headers/HKWorkoutBuilder.h` L253-260
5. `HKWorkoutBuilder.h`, `finishWorkoutWithCompletion:`: "If the returned workout is nil, an error may have occurred in which case error will be non-nil. If both workout and error are nil then finishing the workout succeeded but the workout sample is not available because the device is locked." Swift signature uses `_Nullable_result`, i.e. `func finishWorkout() async throws -> HKWorkout?`. [source-code] same file L218-226
6. Doc page `finishWorkout(completion:)` repeats it: "If both this and the error parameter are nil then finishing the workout succeeded but the workout sample is not available because the device is locked." and "You must call endCollection(withEnd:completion:) before calling this method." [official-doc] https://developer.apple.com/documentation/healthkit/hkworkoutbuilder/finishworkout(completion:)
7. Apple Frameworks Engineer, Dec 2021: "If the device is locked, finishing a workout will succeed but will not be able to return the HKWorkout object. You'll be able to query for that object once the device unlocks again." [official-doc (Apple staff forum reply)] https://developer.apple.com/forums/thread/695853
8. `HKWorkoutRouteBuilder` doc overview: "To create a workout route, use seriesBuilder(for:) to instantiate a HKWorkoutRouteBuilder, and provide it with location data throughout the workout. After the workout ends, call the builder's finishRoute(with:metadata:completion:) method to construct the route. Instantiating a HKWorkoutRouteBuilder directly is discouraged." [official-doc] https://developer.apple.com/documentation/healthkit/hkworkoutroutebuilder
9. Article "Creating a workout route": obtains the builder with `workoutBuilder.seriesBuilder(for: HKSeriesType.workoutRoute()) as? HKWorkoutRouteBuilder`, then "After saving the workout, add any remaining locations to the route builder and call finishRoute(with:metadata:completion:)." It also says "Don't add any locations whose accuracy is greater than 50 meters. For best results, try to keep the time between locations to 3 seconds or less." and "You can only associate a route with a single workout." [official-doc] https://developer.apple.com/documentation/healthkit/creating-a-workout-route
10. `finishRoute(with:metadata:completion:)` doc: "You must have already saved this workout to the HealthKit store." "You must call finishRoute(with:metadata:completion:) before the system deallocates the builder. Failure to do so results in a loss of all route data added to the builder." "This method fails if you haven't added any location data to the builder." [official-doc] https://developer.apple.com/documentation/healthkit/hkworkoutroutebuilder/finishroute(with:metadata:completion:)
11. Only empirical report found (developer, not Apple staff), Dec 2021, using `builder.seriesBuilder(for: .workoutRoute())` + `insertRouteData` + `endCollection` + `finishWorkout()` and **no** `finishRoute`: "this code never reports an error and the route is associated with the workout only when the iPhone is unlocked when saving. If this code is executed on a locked iPhone, the workout is created, the route is created (both can be seen in the Health application) but the route is not associated with the workout." Same author later reports `healthStore.save(hkworkout)` + direct `HKWorkoutRouteBuilder` also failing while locked; a third party works around it by checking `UIApplication.shared.isProtectedDataAvailable` and deferring the route until unlock. No Apple reply in that thread. [secondary] https://developer.apple.com/forums/thread/695845
12. Net: header (facts 3–4) says the series builder obtained via `seriesBuilder(for:)` is finished by `finishWorkout`; two doc pages (facts 8–9) say to call `finishRoute` afterwards. Fact 11 supports the header when unlocked and shows the locked case yields a saved-but-unassociated route, not data loss. Which of the three outcomes (auto-associated / orphan route / error on explicit `finishRoute` after auto-finish) occurs on iOS 26 is UNRESOLVABLE-WITHOUT-DEVICE-TEST (test in §5). ### Item 6 — Expo bridge threading and payload limits

37. Expo docs: `AsyncFunction` "Defines a JavaScript function that always returns a `Promise` and whose native code is by default dispatched on a different thread than the JavaScript runtime runs on." "It is possible to change the native queue of `AsyncFunction` by calling the `.runOnQueue` function". Kotlin: "By default, suspend functions are dispatched on the module's coroutine scope... all unfinished suspend functions will be canceled when the module is deallocated." No Swift async/await variant, no payload-size guidance documented. [official-doc] https://docs.expo.dev/modules/module-api/ (sdk-57 `module-api.mdx` L133, L193, L220)
38. Closure-style Swift `AsyncFunction` (`AsyncFunctionDefinition.swift`, identical in 56.0.24 and sdk-57): `private let defaultQueue = DispatchQueue(label: "expo.modules.AsyncFunctionQueue", qos: .userInitiated)` — a **file-private global serial queue shared by every closure-style AsyncFunction of every module in the process**; `let queue = queue ?? defaultQueue`. Arguments are converted on the JS thread first ("Arguments must be converted on the JS thread, before we jump to another thread"). If the runtime has no scheduler the body runs inline "to avoid touching the runtime from a background queue." [source-code] https://raw.githubusercontent.com/expo/expo/sdk-57/packages/expo-modules-core/ios/Core/Functions/AsyncFunctionDefinition.swift L20, L133-140
39. `Promise.resolve/reject` are safe from any thread: `tryResolve` does `runtime.schedule(priority: .immediate) { let value = try appContext.converter.toJS(value, dynamicType); resolver(value) }` — both the JS conversion and the resolver run on the JS runtime scheduler, never on the caller's thread. So resolving from a HealthKit completion/`HKWorkoutRouteQuery` callback queue is correct by construction; the kingstinct 13.3.1 SIGSEGV class (continuations resumed off-thread into Nitro/JSI) does not apply to Expo's `Promise`. [source-code] local `expo-modules-core@56.0.24/ios/Core/Promise.swift` L80-92
40. Swift-concurrency variant (`ConcurrentFunctionDefinition.swift`, `typealias ClosureType = @Sendable (Args) async throws -> sending ReturnType`): `call` is `@JavaScriptActor`, converts args there, `try await body(args)` (or `callBodyOnMainActor` only when `requiresMainActor`, i.e. view functions), then `try await appContext.runtime.execute { try appContext.converter.toJS(returnValue, ~ReturnType.self) }`. A nonisolated `async` closure awaited from an actor runs on the global concurrent executor, not on the JS actor (SE-0338 semantics [secondary]). Conversion of the *whole* return value happens in one synchronous block on the JS thread in both variants. Changelog: "Added support for concurrent (async/await) functions in Swift (#20645)". [source-code] local `ConcurrentFunctionDefinition.swift` L20, L59-90; `CHANGELOG.md` L1795
41. New in SDK 56/57: `@OptimizedFunction` / `@JS` macros (`ExpoModulesMacros.swift`) produce `OptimizedAsyncFunctionDefinition` whose ObjC++ bridge runs the block on `dispatch_get_global_queue(QOS_CLASS_USER_INITIATED, 0)` and resolves via `jsInvoker().invokeAsync` ("so the resolve and reject callbacks are dispatched back onto the JS thread"); `runOnQueue` is a no-op there. [source-code] local `ios/JS/EXOptimizedFunctionUtils.mm` L249-314; `ios/Core/Functions/OptimizedAsyncFunctionDefinition.swift`
42. No measurement of 10k–40k-record promise vs 500-point `sendEvent` chunks exists in any source; it must be measured (§5). What the source establishes: cost is paid once, synchronously, on the JS thread (`toJS` of the full array / of each event payload); there is no hard cap in expo-modules-core. [source-code] facts 39–41
43. Android (API ≥ 34, `HealthConnectClientUpsideDownImpl` → platform `android.health.connect`): `ParcelUtils.putToRequiredMemory` writes the records parcel into `SharedMemory.create("RecordsParcelSharedMemory", size)` whenever `dataParcel.dataSize() > IPC_PARCEL_LIMIT` where `IPC_PARCEL_LIMIT = IBinder.getSuggestedMaxIpcSizeBytes() / 2` and `getSuggestedMaxIpcSizeBytes()` returns `MAX_IPC_SIZE = 64 * 1024` → 32 KiB. `RecordsParcel.writeToParcel` (used by insert and by `ReadRecordsResponseParcel`) goes through it. So `readRecords`/`readRecord`/`insertRecords` payloads are **not** bounded by the 1 MB Binder buffer. [source-code] https://android.googlesource.com/platform/packages/modules/HealthFitness/+/refs/heads/main/framework/java/android/health/connect/internal/ParcelUtils.java ; .../aidl/RecordsParcel.java L91 ; https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/os/IBinder.java L198-207
44. But per-record size is capped on insert: `RateLimiter.RECORD_SIZE_LIMIT_IN_BYTES_DEFAULT_FLAG_VALUE = 1000000` ("The maximum size in bytes of a single record a client can insert in one go"), `CHUNK_SIZE_LIMIT_IN_BYTES_DEFAULT_FLAG_VALUE = 5000000` per call; enforced in `insertRecords`/`updateRecords` via `enforceMemoryRateLimit(recordsParcel.getRecordsSize(), recordsParcel.getRecordsChunkSize())` → `checkMaxRecordMemoryUsage` throws `HealthConnectException(ERROR_RATE_LIMIT_EXCEEDED, "Record size exceeded the single record size limit: 1000000, was: N")`. Record size = parcel bytes of that record (`RecordsParcel` computes it from `dataAvail()` deltas). [source-code] AOSP `RateLimiter.java` L42-44, L68-69, L189-199; `HealthConnectServiceImpl.java` L506-507, L3282-3285
45. `ExerciseRoute.Location.writeToParcel` = `writeLong(time) + writeDouble(lat) + writeDouble(lng) + 3 × (writeBoolean [+ writeDouble])` = 36 bytes (no optionals) to 60 bytes (altitude + both accuracies) per point → the 1,000,000-byte record cap corresponds to roughly **16.6k (all fields) – 27k (bare) points** for one `ExerciseSessionRecord` with route, minus session overhead. [source-code + arithmetic] https://android.googlesource.com/platform/packages/modules/HealthFitness/+/refs/heads/main/framework/java/android/health/connect/datatypes/ExerciseRoute.java L298-314
46. Consent-dialog path: `RouteRequestActivity.finishWithResult` does `result.putExtra(EXTRA_EXERCISE_ROUTE, route); setResult(RESULT_OK, result)` — an ordinary Activity-result `Intent`, which crosses Binder with no shared-memory fallback. `TransactionTooLargeException` doc: "The Binder transaction buffer has a limited fixed size, currently 1MB, which is shared by all transactions in progress for the process." So routes approaching the record cap can fail on the *dialog* path even though `readRecords` would deliver them. ## 3. Design implications for a minimal-options unified API

1. **iOS write: one code path, builder-owned route, plus a `pending` outcome.** Use `HKWorkoutBuilder` + `seriesBuilder(for:)` (header-sanctioned; direct init is "discouraged"). After `finishWorkout()`:
   - workout non-nil → if the device test shows the route was auto-associated, do nothing; if not, call `finishRoute(with:)` (decide once from the test, do not expose an option).
   - workout nil / no error → return `{ status: "pending", localId }` and keep the points on disk; retry association after `UIApplication.isProtectedDataDidBecomeAvailableNotification` by querying the workout via `HKMetadataKeySyncIdentifier` (the builder's metadata must carry the app's sync id + version so the retry can find it) and, if no route is associated, attach with a fresh `HKWorkoutRouteBuilder` + `finishRoute(with:)`. This is exactly the contract healthkit-write proposed; it stays.
   - Never expose "use series builder vs direct builder" as an option.
2. **Android/Gradle floors (no options):** ship the library with `minSdk 26` in its own `build.gradle` and `connect-client:1.1.0`; document for consumers "set `android.minSdkVersion = 26` (expo-build-properties) or add `tools:overrideLibrary="androidx.health.connect.client"`" — the exact merger error (fact 20) goes into the README so people recognise it. Do not touch `compileSdk` (36 is fine for 1.1.0 / alpha01–03).
3. **No `#available(iOS 16)` anywhere.** Deployment target 16.4 (fact 13/21). Keep availability checks only for effort score (18) and iPhone workout sessions (17/26), which this library does not use.
4. **Route permission string is a constant in our Kotlin code**, not `HealthPermission.*`. Expose it in JS as a capability flag, not a permission the user can "request": on Android the unified `requestAuthorization` should (a) include it in the contract input (harmless, fact 48), (b) report `routes: "granted" | "perRouteConsent"` from `getGrantedPermissions()` afterwards, never `denied`, because denial is not observable (fact 57).
5. **Route read on Android is two-tier and must be modelled, not hidden:** `getRoute(id)` returns `{ points }` or `{ consentRequired: true }`; a separate `requestRouteConsent(id)` launches `ExerciseRouteRequestContract` (must be called from a resumed Activity; result `null` is ambiguous — map to `"unavailable"`). Document: after "Always allow" (Android 15+ only, fact 51) `getRoute` succeeds while the app is in the foreground; from background/WorkManager it is *always* `consentRequired` for foreign sessions (facts 55–56) → the sync engine must fetch routes while the app is TOP and cache them.
6. **Energy:** write `ActiveCaloriesBurnedRecord` only; read `ACTIVE_CALORIES_TOTAL`; do **not** fall back to `ENERGY_TOTAL` for `activeEnergyKcal` (it is synthesised from BMR, fact 35). If total energy is wanted at all, expose it as a separate optional `totalEnergyKcal` field that is HC-only (HK has no "total" sample; HK `totalEnergyBurned` is *active*, fact 28). Declare only `ACTIVE_CALORIES_BURNED` read/write on Play.
7. **HK totals:** normalise `distanceMeters`/`activeEnergyKcal` with provenance `associated | total | derived` (tiny enum, not an option); order: `statistics(for:)` → deprecated total → time-window statistics (only when a caller passes `allowDerived: true`? No — keep it automatic and tag it; an option here buys nothing).
8. **Route payload:** points cross the bridge once, converted on the JS thread (facts 39–42). Until measured, return `getRoute` as one array but cap nothing; add an internal `routeChunkSize` only if the device test shows JS-thread stalls > ~50 ms at 40k points. On Android, reject/route-downsample at **write** time when the serialized route would exceed ~900 kB (fact 44–45) and surface a typed `RouteTooLarge` error instead of `ERROR_RATE_LIMIT_EXCEEDED`.
9. **Threading in the Swift module:** long HealthKit work must not sit on the shared `expo.modules.AsyncFunctionQueue` (fact 38) because it would serialise *all* closure-style async functions of *all* Expo modules in the app. Either take a `Promise` argument and return immediately (HealthKit callbacks resolve it) or use `async throws` bodies (off-actor, fact 40). Never `.runOnQueue(.main)` for HealthKit calls.

## 4. Pitfalls / gotchas

1. `finishWorkout()` returning `nil` without throwing is *success* — treating it as failure and re-saving creates duplicate workouts after unlock (facts 5–7).
2. With the `seriesBuilder` path on a locked phone the route may be saved **unassociated** (fact 11): a later "attach route" retry must first check for an existing orphan `HKWorkoutRoute` (predicate on `HKMetadataKeySyncIdentifier` if you set it on the route builder via `addMetadata`) or it will double-write.
3. `finishRoute` with zero points throws; filter `horizontalAccuracy > 50 m` *before* insert (fact 9–10) and skip the route entirely when nothing survives.
4. alpha05's "minSdk 24" release note is false in the artifact (fact 17) — do not relax the minSdk policy on the strength of the changelog.
5. `1.2.0-alpha03` declares `minCompileSdkExtension=19` (fact 18): if anyone ever bumps to it, the build may fail with the extension-level variant of the AAR-metadata error even on compileSdk 36.
6. AGP's `minCompileSdk` check fails at `checkDebugAarMetadata`, so `./gradlew :app:dependencies` "passing" proves nothing (fact 19).
7. `totalEnergyBurned` emits a deprecation warning under Swift 6 strict settings; `totalDistance` does not (facts 27–28) — a `-warnings-as-errors` CI will break only on the energy accessor.
8. `ENERGY_TOTAL` is never "missing" — it silently includes synthesised BMR (fact 35). Comparing it to HK active energy under-/over-states by resting energy (domain-model pitfall 13 confirmed).
9. Writing to `TotalCaloriesBurnedRecord` *and* `ActiveCaloriesBurnedRecord` for the same interval double-declares data types on Play and double-counts in HC totals (fact 32).
10. Expo's default `AsyncFunction` queue is **one serial queue for the whole app** (fact 38): a 2-second HealthKit read in a closure body blocks `expo-file-system`, `expo-image-picker` etc. Use `Promise`-arg or `async throws` bodies.
11. `Promise.resolve` after `AppContext` deallocation is a silent no-op (`guard let appContext ... else { return }`, fact 39) — long HealthKit queries outliving a reload never reject; put a timeout in JS.
12. Android single-record cap: a session with a ~17k-point route (60 B/point) is rejected at insert with `ERROR_RATE_LIMIT_EXCEEDED`, which reads like a quota problem, not a size problem (facts 44–45).
13. Route via the consent dialog crosses Binder as a plain Intent extra (fact 46): the largest routes that `readRecords` can deliver (shared memory) may not survive the dialog path → for big foreign routes the only reliable path is "Always allow" + foreground `readRecord`.
14. `RouteRequestActivity` cancels silently when the caller's manifest lacks `READ_EXERCISE_ROUTES` (fact 52) — a config-plugin bug shows up as "user denied" in analytics.
15. The 30-day wall also applies to the route dialog (`isSessionInaccessible`, fact 52): without `READ_HEALTH_DATA_HISTORY` the dialog never opens for older sessions, returning `null`.
16. `READ_EXERCISE_ROUTES` denied with "Don't allow" repeatedly becomes `USER_FIXED` → dialog never shows again (fact 52); the app cannot detect this (fact 57); surface a "open Health Connect settings" path.
17. Android 14 devices have no "Always allow" (fact 51): on API 34 every foreign route needs a per-route dialog, forever.
18. `READ_HEALTH_DATA_IN_BACKGROUND` does not unlock foreign routes (facts 55–56); don't request it "for routes" — it only costs a Play justification.
19. Foreground is evaluated **per call** (fact 54): a sync loop started in `onResume` that continues after the user leaves flips to `OWN` mid-loop and starts returning `ConsentRequired` for the remaining sessions.
